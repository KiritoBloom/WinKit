# WinKit — Full Refocus, Hardware Observability, Diagnostics, and Tool-Surface Overhaul

You are working directly inside the existing **WinKit** repository.

Your job is to substantially improve WinKit into a focused, production-quality **Windows observability and diagnostics MCP server for AI agents**.

Do not treat this as a greenfield project.

Do not throw away working architecture.

Do not create a second architecture beside the existing one.

First understand the repository deeply, then modify the existing implementation in place.

The current repository already has a strong separation between MCP/tool definitions, providers, Windows implementations, permissions, models, diagnostics, testing, packaging, and documentation. Preserve that general philosophy unless you find a concrete technical reason that it must change.

The most important goal is not "add as many features as possible."

The goal is:

> Make WinKit the thing an AI agent calls when it needs to understand what is happening on a Windows machine, why the machine is unhealthy, what resource is responsible, and what evidence supports that conclusion.

WinKit should be **agent-native**, **evidence-first**, **Windows-native**, **read-only by default**, fast, honest about unavailable telemetry, and focused.

# 2. Establish the new product boundary

The primary product identity should become:

> **WinKit is a Windows-native observability and diagnostic engine for AI agents.**

It is NOT primarily:

* a Chrome debugger
* a web-development environment
* a browser automation server
* a generic Windows API wrapper
* a collection of unrelated utilities

The core question should be:

> "What is happening on this Windows machine, and what evidence explains it?"

The second question should be:

> "What specific subsystem or resource is likely responsible?"

The agent should not have to manually combine dozens of primitive measurements every time.

WinKit should do that work.

# 6. Build a real hardware telemetry subsystem

This is the most important addition.

WinKit should gain a first-class hardware telemetry layer.

The system must be designed around **sensor discovery**, not assumptions.

Do NOT assume every machine has:

* CPU temperature
* GPU temperature
* motherboard temperature
* battery temperature
* SSD temperature
* fan speed
* power readings
* every thermal zone

Some systems will expose many sensors.

Some will expose very few.

Some will expose only OS thermal zones.

Some will expose vendor-specific sensors.

The API must represent this honestly.

---

# 7. Create a hardware/sensor provider abstraction

Introduce or extend a provider abstraction suitable for hardware telemetry.

It must be capable of representing:

* sensor identity
* sensor class/type
* physical component
* current value
* unit
* source
* confidence/reliability
* availability
* timestamp
* optional hardware metadata
* optional min/max
* optional state/status
* optional throttling information

Do not hard-code the assumption that all sensors are temperatures.

Design the abstraction so it can later accommodate:

* temperature
* fan speed
* voltage
* current
* power
* clock rate
* battery metrics
* utilization

but implement temperature/thermal telemetry first.

A sensor should conceptually be able to answer:

```text
What is this?
What component does it belong to?
What is its current value?
Where did the value come from?
How reliable is the source?
When was it sampled?
Why might it be unavailable?
```

# 8. Implement Windows thermal-zone support first

Use Windows-native mechanisms wherever available.

Investigate and implement support for Windows thermal-zone telemetry through the appropriate Windows APIs/performance-counter/ACPI mechanisms available to user-mode applications.

Do not assume a thermal zone is the CPU.

A thermal zone might correspond to:

* CPU-related thermal management
* chassis/skin temperature
* motherboard
* battery area
* another thermal region

Therefore represent thermal zones independently from semantic labels like `cpu_temperature`.

The raw result should preserve:

```text
thermal_zone_id
name
temperature
source
timestamp
availability
```

Where available, capture relevant thermal-management state such as:

* passive cooling/throttling
* throttle percentage
* thermal state
* throttle reason
* active/passive state

Do not fabricate values.

If only a generic thermal zone exists, report it as a generic thermal zone.

Do not incorrectly label it "CPU temperature."

# 9. Investigate CPU-specific sensor access

Implement CPU telemetry through hardware-aware providers where reliable access is possible.

Support Intel first if that is the simplest reliable implementation.

Then support AMD.

The implementation should investigate the proper hardware/Windows mechanisms rather than relying on undocumented guesses.

Possible information may include:

* package temperature
* core temperatures when available
* CPU frequency
* effective frequency if available
* thermal throttling
* package power where available
* processor utilization

Do not assume every CPU exposes core temperatures.

Do not fail the entire hardware snapshot because one CPU metric is unavailable.

Example:

```json
{
  "sensor": "CPU Package",
  "type": "cpu_package_temperature",
  "temperature_c": 91.0,
  "source": "hardware_sensor",
  "availability": "available"
}
```

If only an OS thermal zone exists:

```json
{
  "sensor": "Thermal Zone 0",
  "type": "thermal_zone",
  "temperature_c": 58.0,
  "source": "windows_thermal_zone",
  "availability": "available"
}
```

These must remain semantically distinct.

# 13. Add thermal throttling as a diagnostic concept

Do not stop at temperature collection.

Correlate:

```text
temperature
+
CPU/GPU frequency
+
utilization
+
thermal state
+
time
```

The diagnostic engine should be able to distinguish:

### High temperature without clear throttling

```text
Temperature: 94°C
Frequency: normal
Throttle: not observed
```

Do not claim thermal throttling.

### High temperature with frequency reduction

```text
Temperature: 96°C
Frequency: significantly below baseline
Throttle state: active
```

Potential finding:

```text
Thermal throttling likely
```

### High CPU with normal temperature

Do NOT diagnose thermal throttling.

Potential finding:

```text
CPU contention likely
```

### Low frequency with low utilization and no thermal evidence

Do NOT automatically claim thermal throttling.

State that the evidence is incomplete.

This is extremely important.

WinKit must never convert correlation into false certainty.

# 30. Improve trend/sampling support

WinKit already has time-window diagnostics.

Extend this philosophy to hardware.

Thermal readings especially need time.

A single reading:

```text
CPU: 96°C
```

is much less useful than:

```text
10-second observation

temperature:
  79 → 84 → 88 → 91 → 95 → 96°C

frequency:
  2.8 → 2.7 → 2.5 → 2.1 → 1.6 → 1.2 GHz
```

The diagnostic engine can then recognize a trend.

Add bounded sampling for:

* temperature
* frequency
* utilization
* disk activity
* network quality
* battery/power

Do not create infinite streams.

Use bounded windows.

Respect the existing timeout and payload safety model.

# 94. Final instruction

Do not optimize for the number of features added.

Optimize for this:

> **An AI agent should be able to ask WinKit a broad question about a Windows machine and receive fast, structured, evidence-backed information that actually helps explain what is happening.**

The finished product should feel like a coherent diagnostic system, not a bag of Windows APIs.

When deciding between adding another feature and improving correlation, correctness, completeness, performance, or agent usability, prefer the latter.

When deciding between exposing another low-level tool and making an existing high-level diagnostic capability smarter, prefer making the high-level capability smarter.

When deciding between claiming support and honestly reporting "unavailable", choose "unavailable".

When deciding between preserving an unrelated application integration in core and keeping the product focused, keep the product focused.

The end result should be a **focused Windows observability platform with hardware awareness, thermal awareness, storage health, network awareness, power awareness, and evidence-first diagnosis**, while preserving the project's existing Rust/MCP architecture, security model, deterministic testing strategy, and local-first philosophy.
